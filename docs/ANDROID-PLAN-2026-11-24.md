# План развития Android-клиента POSCloud

Дата: 24.11.2026. Текущая версия: **1.0.35** (versionCode 10035), релиз
[v1.0.35](https://github.com/reznikov73/POSCloud/releases/tag/v1.0.35).

Документ фиксирует идеи по развитию Android-клиента: что делаем, зачем, сколько
это стоит и по каким признакам считаем готовым. Порядок разделов соответствует
приоритету: сверху то, что даёт больше пользы при меньшем риске.

## Ограничения архитектуры

Клиент — чистое Go-приложение на Fyne, собирается `fyne package` (gomobile).
Java-классов в проекте нет: Fyne приносит свою `GoNativeActivity` уже
скомпилированной в `classes.dex`, поэтому добавить свой Java-код в сборку
нельзя. Всё, что требует системы, делается через JNI из Go (`internal/camera` —
рабочий пример: JVM, MediaStore, `ACTION_IMAGE_CAPTURE`).

Отсюда три категории работ:

| Категория | Что можно | Проверка |
|---|---|---|
| **A. Чистый Go** | логика, экраны, движок, работа с файлами | `go test`, скриншоты через `software`-драйвер |
| **B. Небольшой JNI** | вызовы системных сервисов из Go | сборка под android + проверка на телефоне |
| **C. Нативный слой** | служба, камера-preview, SAF, виджет | нужен Java/Kotlin и своя сборка (Gradle), отдельная ветка |

Ограничение B: `JNI_GetCreatedJavaVMs` берётся через `dlopen("libnativehelper.so")`,
на старых прошивках возможен отказ — везде предусмотрен понятный текст ошибки.

## Волна 1. Быстрые победы (категория A)

Делаются без телефона: логика покрывается тестами, интерфейс — рендером.

### 1. Тихие часы и расписание синхронизации

**Зачем.** Ночью синк не дёргает сеть и батарею, утром файлы уже на месте.

**Как.** В настройках: окно «не синхронизировать с 23:00 до 07:00». Движок уже
умеет паузу между циклами — достаточно не запускать цикл в окне и возобновлять
после.

**Объём.** 1 день. **Готово, когда:** цикл не стартует в окне, после окна
возобновляется сам, в журнале одна понятная запись о паузе.

### 2. Экономия трафика

**Зачем.** Точка работает на мобильном интернете; скачивание большого файла
незаметно съедает лимит.

**Как.** Две настройки: «не скачивать файлы больше N МБ» и «пауза, если скорость
ниже порога» (движок считает скорость по времени передачи блоков). Пропущенные
файлы помечаются в журнале, а не теряются.

**Объём.** 1–2 дня. **Готово, когда:** файл больше лимита не скачивается, в
журнале причина, после снятия лимита он скачивается.

### 3. Экран «Недавние»

**Зачем.** Первое, что хочется открыть на телефоне, — что изменилось, а не
дерево папок.

**Как.** Лента из SSE `/events`, который клиент уже слушает: кто, когда, что
загрузил или удалил. Тап по записи — переход к файлу или папке.

**Объём.** 2 дня. **Готово, когда:** события появляются без ручного обновления,
история переживает перезапуск приложения.

### 4. Разрешение конфликтов

**Статус на 24.11.2026: сделано** (шаг 2 из «Порядка работ»). В движок добавлен
API (`engine/conflicts.go`: `Conflicts`, `ResolveConflictKeepLocal`,
`ResolveConflictKeepServer`), на «Файлах» — карточка «Конфликты»: список копий,
выбор «моя версия» / «серверная», проигравшая копия удаляется и локально, и на
сервере. Без связи «моя версия» откладывается с ошибкой, конфликт остаётся
в списке. Точность из плана про `engine/conflicts.go` оказалась предсказанием:
файла не было — теперь есть.

**Зачем.** Сейчас конфликтные копии просто лежат в папке и копятся.

**Как.** В движке есть `conflicts.go` и конфликтные копии. Экран «Конфликты»:
пара файлов, выбор «моя версия» / «серверная», удаление лишней копии одним
нажатием.

**Объём.** 2–3 дня. **Готово, когда:** конфликт виден списком, выбор применяется
и синхронизируется, копия-проигравшая удаляется.

### 5. «Держать на телефоне» и автоочистка

**Зачем.** Память телефона кончается; сервер — источник истины.

**Как.** Метка «держать локально» на файле/папке (не удаляется при чистке) и
настройка «удалять локальные копии, не открывавшиеся N дней». В движке уже есть
`ClearLocalCopy`.

**Объём.** 2–3 дня. **Готово, когда:** помеченные файлы не удаляются, остальные
удаляются по сроку и скачиваются заново по требованию.

### 6. Поиск и статистика хранилища

**Зачем.** Дерево на телефоне не масштабируется; нужно найти файл по имени и
понять, сколько занято.

**Как.** Поиск по имени в дереве; экран «Хранилище»: занято локально, всего на
сервере, квота (на сервере есть `quota.go`).

**Объём.** 2 дня. **Готово, когда:** поиск находит файл в свёрнутых папках,
цифры совпадают с сервером.

### 7. PIN/биометрия на запуск

**Зачем.** Папка синхронизации видна любому, кто взял телефон.

**Как.** Код на вход, скрытие превью в списках, автоблокировка после N минут.

**Объём.** 1–2 дня. **Готово, когда:** без кода приложение не показывает файлы,
код не хранится в открытом виде (хэш + соль).

## Волна 2. Небольшой JNI (категория B)

### 8. Foreground service

**Зачем.** Сейчас синхронизация живёт, пока приложение открыто. Это главное
ограничение клиента.

**Как.** Служба с постоянным уведомлением «POSCloud синхронизирует». Требует
Java-класса службы, то есть сборки с dex — это уже категория C по способу
сборки, но по объёму ближе к B.

**Объём.** 3–5 дней. **Готово, когда:** синк продолжается при погашенном экране,
уведомление показывает состояние и имеет кнопку «Пауза».

### 9. Только по Wi-Fi и пауза в роуминге

**Зачем.** Экономия трафика и нервов.

**Как.** Тип сети через `ConnectivityManager` (один JNI-вызов), настройка
«синхронизировать только по Wi-Fi».

**Объём.** 2 дня. **Готово, когда:** на мобильной сети цикл не стартует, в
журнале причина; на Wi-Fi возобновляется.

### 10. Системные уведомления о событиях

**Зачем.** Не заставлять человека держать приложение открытым.

**Как.** «Синхронизация остановилась», «Конфликт файлов», «Загружено N файлов»,
«Доступна новая версия».

**Объём.** 2–3 дня. **Готово, когда:** уведомление приходит при свёрнутом
приложении и по тапу открывает нужный экран.

### 11. «Поделиться в POSCloud»

**Зачем.** Принимать файлы из других приложений (фото, PDF, чеки) прямо в папку
синхронизации.

**Как.** `intent-filter` на `SEND`/`SEND_MULTIPLE` в своём
`AndroidManifest.xml.in` + передача файлов в Go. Манифест уже свой — это плюс.

**Объём.** 3 дня. **Готово, когда:** «Поделиться» из галереи кладёт файл в папку
и он уезжает на сервер.

## Волна 3. Нативный слой (категория C)

Каждый пункт — отдельная ветка сборки и проверка на устройстве.

### 12. Живой сканер QR в приложении

**Зачем.** Сейчас камера системная: снимок, потом распознавание. Нужен
непрерывный скан с рамкой.

**Как.** CameraX + ZXing в Java-слое, кадры отдаются в Go на распознавание
(наш декодер уже умеет повороты, ч/б, резкость, масштабы).

**Объём.** 1–2 недели. **Риск:** высокий, ломает «чистый Go» в части сборки.

### 13. SAF-доступ к произвольным папкам

**Зачем.** Сейчас доступны только пути в рамках legacy-хранилища; `Documents`
и чужие папки — нет.

**Как.** Storage Access Framework: выбор дерева документов, persistable URI,
чтение/запись через `ContentResolver`.

**Объём.** 1–2 недели.

### 14. Виджет и плитка быстрых настроек

**Зачем.** «Синхронизировать сейчас», «Пауза» и статус — с домашнего экрана.

**Как.** AppWidget + `TileService`, обмен состоянием с Go через файл-состояние
или широковещательные сообщения.

**Объём.** 1 неделя.

## Продуктовые идеи под POS

### 15. Фото-сканы документов

**Зачем.** Чек или накладная снимаются на телефон и уходят в «Документы».
Половина уже есть: камера и запись в папку.

**Как.** Снимок → выпрямление и ч/б → PDF с датой в имени → папка «Документы».
Выпрямление можно начать с простого: обрезка по краям и поворот.

**Объём.** 3–5 дней (без сложного выпрямления — 2 дня).

### 16. Правила по имени файла

**Зачем.** Сейчас правила только по папкам первого уровня.

**Как.** «Всё, что `чек_*.pdf`, — только на сервер», «фото — не больше 5
последних». Шаблоны исключений в движке уже есть — нужен интерфейс и хранение.

**Объём.** 3 дня.

### 17. QR-экспорт настроек

**Зачем.** Перенос конфигурации на новое устройство одним сканом.

**Как.** Расширение QR-подключения: сервер + токен + правила + расписание в один
код.

**Объём.** 2 дня. **Важно:** токен в QR — только для одноразового показа, не
хранить картинку в галерее.

## Как проверяем

- **Логика и экраны:** `go vet ./internal/...`, `go test ./internal/...`,
  скриншоты вкладок через `POSCLOUD_SHOTS` (рендер без телефона).
- **JNI-вызовы:** кросс-сборка `GOOS=android GOARCH=arm64` с NDK, затем
  установка на телефон и проверка сценария вручную.
- **Релиз:** `build.sh` (16-КБ выравнивание, versionCode из версии), затем
  тег и релиз на GitHub с APK.

## Риски

- **JNI без устройства в руках.** Каждый вызов проверяется только на телефоне:
  ошибка в подписи метода даёт исключение, а не падение — поэтому везде текст
  ошибки выводится в диалог и журнал.
- **Нативный слой (категория C)** ломает текущую сборку `fyne package`:
  потребуется своя сборка через Gradle, это отдельное решение, а не «ещё одна
  кнопка».
- **Хранение секретов.** Токены и PIN не писать в открытом виде; QR с токеном —
  только одноразово.
- **Память телефона.** Автоочистка (5) должна появиться раньше массового
  скачивания папок, иначе телефон забьётся.

## Первый шаг

Берём шаг 1 из таблицы: **тихие часы и лимиты трафика**. Оба пункта — чистый Go,
проверяются тестами, не требуют телефона и сразу заметны в работе. После них —
конфликты: они останавливают рост мусора в папке.
